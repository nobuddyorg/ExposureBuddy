# Design decisions

Why things are the way they are, where reading the code once would not tell you. For _what_ exists, see the [Architecture reference](../reference/architecture.md).

## Why there is no backend, and privacy is the product claim

A burst is thirty or fifty full-size phone photos, often of a place the photographer is standing in. Uploading them to a server would make the app slower (a hundred megabytes up a mobile link before anything happens), more expensive (compute and storage for every visitor) and, above all, something a visitor has to trust. Keeping every byte on the device removes all three: the app is a static export on GitHub Pages, the only network traffic is the app shell itself, and the footer's _Your photos never leave this device_ is a statement about the architecture, not a policy.

That claim is enforced, not hoped for. The document's CSP (`connect-src 'self'`, `img-src 'self' blob:`) leaves no origin to send pixels to; the workers, which a static host cannot hand a CSP of their own, are held to the same rule by the architecture check that lets `vision/` and `workers/` import nothing that reaches the network, and by review; there is no analytics, no third-party script and no font fetched at runtime; and CLAUDE.md rules out any feature that needs a server. The cost is that everything the app does has to fit in a browser tab on a phone, which is what most of the decisions below are about.

## Why the kernels are plain TypeScript, not OpenCV.js, WASM or WebGPU

OpenCV.js would have given ORB, `findHomography` and `warpPerspective` for free, at the price of an eight-megabyte WASM binary in a PWA that promises to work offline, a black box nobody here can step through, and a dependency whose build is its own project. WebGPU would make the warp and the stack fast, but Safari and Firefox support arrived late and unevenly, and a second code path for the browsers without it would double what has to be tested.

Plain TypeScript over typed arrays keeps the whole pipeline in one language, debuggable in the browser and in Node, and, decisively, **testable the way the rest of the project is tested**: every kernel runs under Vitest on a synthetic image with a known answer, carries property tests where a property is easy to state, and sits on the mutation-testing list, none of which is possible for code inside a WASM blob. The cost is speed. Measured on a laptop, a twelve-frame burst at a working long edge of 1600 px aligns and stacks in a few seconds with the worker pool; a fifty-frame burst on a phone is tens of seconds. That is acceptable for an MVP, and the hard rule that `vision/` is pure keeps the door open: a kernel can be swapped for a WASM or GPU implementation behind the same function signature and the same tests when a measurement says it is worth it.

## Why ORB-style features and a RANSAC homography, not phase correlation or dense flow

A hand-held burst drifts in translation, rotation and a little scale, and a phone rotated by a degree between frames is the normal case. Phase correlation recovers translation only; extending it to rotation and scale (a log-polar pass) costs more than it saves and still assumes the whole frame moves rigidly. Dense optical flow would handle everything, including the walker, but at a cost per pixel per frame that a phone cannot pay for fifty frames, and it would align the moving people too, which is exactly what the app must not do.

Sparse features are the middle: FAST corners are cheap, the intensity-centroid orientation and rotated BRIEF make them rotation-invariant, and Hamming matching over 256-bit descriptors is a handful of XOR-popcounts per pair. RANSAC over a homography then does two jobs at once: it fits the camera motion and it **rejects the correspondences on moving objects as outliers**, so the walker never pulls the alignment. A homography is the right model because the scene is far away relative to the camera's motion (a street from a fixed spot is close to a rotating camera), and the sanity check on scale, skew and perspective refuses the degenerate fits that a few clustered inliers can produce. Detection runs on a grayscale copy no larger than the alignment size, bucketed on a grid so corners spread over the whole frame rather than piling up on the one busy façade, which is what makes the homography hold across the frame.

## Why the middle frame is the reference

Every other frame is warped into the reference's coordinates, so the reference decides the crop and the amount of warping. Camera drift accumulates over a burst; the first frame can be a full drift away from the last, while the middle frame is at most half a drift from either end. Picking it minimises the largest transform any frame needs, which keeps more of every frame inside the crop and keeps the bilinear resampling gentle. It is also the one decision the user does not have to make: a reference picker would be a control almost nobody would use well.

## Why an unalignable frame is skipped, not guessed

When RANSAC finds too few inliers (below a minimum count and a minimum share of the matches), the honest answer is that the frame's relation to the reference is unknown. Blending it in with the best-guess homography, or with the identity, would smear the static scene, which is the one thing the app promises to keep sharp, and it would do so silently. So the frame is dropped, its status line says _skipped_ with its match counts, and the result reports how many frames went in. A burst where too few frames align at all ends on the error screen with a hint about shooting from one spot, rather than a plausible-looking image made of two frames. This is the fail-fast rule in CLAUDE.md applied to the pipeline: a wrong image that looks right is the worst outcome this architecture can produce.

## Why the median is the scene, the mean is the ghosts, and how the composite is built

A moving person covers a given pixel in a few frames and leaves it in the rest. Over enough frames the per-pixel **median** therefore lands on the background: it is what a long exposure shows once the moving things have averaged out, minus the ghosts. The **mean** is the literal long exposure, background plus every passer-by at a fraction of their opacity. Keeping the background estimates and the mean lets the look be a function of a few buffers instead of the whole stack, so the sliders re-render in the stack worker without touching the aligned frames again.

The composite is `background + ghostStrength × blur(mean − background) + glow × blur(max(mean − background, 0))`, the background being the median unless another estimate is chosen. The difference `mean − median` is the ghosts alone, so `ghostStrength` scales them from none (the empty scene) to the plain mean. **Blur** is applied to that difference, not to the whole image, so the static scene stays as sharp as the median while the ghosts smear as a longer exposure would. **Glow** takes only the positive part of the difference, which is where something brighter than the background passed (headlights, a white shirt), blurs it and adds it on top: the bloom of a light trail. Both blurs are separable running-sum box blurs, three passes to approximate a Gaussian, so their cost does not grow with the radius.

**Light trails** swap the mean for the brightest value each pixel saw. The mean spreads a passing headlight over every frame and dims it by the frame count; a long exposure on film does not, because light only adds. The per-pixel maximum is what a lighten-stack does and costs one more layer in the stack, three bytes per pixel. It goes through the same formula, so at full strength, without blur or glow, the result is the maximum itself, and the sliders shape trails the way they shape ghosts.

The sliders open at values that depend on the burst, not at one constant. With ten or more frames a mover's copies overlap and the look is 60 % ghosts and a blur of 0.25 % of the long edge. With fewer, a mover shows as a few separate copies, so the ghosts start fainter (a twentieth of a percent per frame, never below 25 %) and the blur grows up to three times, which joins the copies into a streak. The blur is a share of the long edge because a fixed 4 px is a hairline on a 2,400 px result and a smear on a 600 px one; the blur slider's range follows the size the same way (2 % of the long edge, at least 32 px, at most 128). The result screen also names the photos that were left out, since "3 of 4 aligned" alone does not say what to change: a frame is skipped because the camera moved.

### Four backgrounds, to compare

The median fails where a mover covers half the frames or more, and over few frames it is noisy. The stack therefore also computes a trimmed mean (the middle half, so one outlier in four cannot pull it far), a clipped mean (everything within three MAD-sigmas of the median, at least eight levels, so a near-constant pixel is not clipped into noise) and the median of the densest 32-level window (the mode: the colour most frames agree on, even when the crowd's clothes all differ). The result screen switches between them because which one wins depends on the scene; this is an experiment, and the ones that never win can be dropped again. Each costs 4 bytes per working pixel, which `STACK_BYTES_PER_PIXEL` accounts for, and a sort of the samples per channel and pixel. The window's median rather than its mean, because a near outlier inside 32 levels would otherwise pull the mode off the scene.

The result screen keeps the controls small so the picture stays the subject. Each slider is one line (label, value, an info button) plus the track; its help text opens on demand, and stays the slider's accessible description either way. Compare is a button on the corner of the image, next to the press-and-hold gesture that does the same, and Start over is a quiet button beside Save. On a phone the sliders fold behind an "Adjust the look" bar, so the image and Save fit on one screen; on a desktop the bar is not shown and the sliders are always open beside the image.

## Why exposure is normalised per channel

Phone cameras meter every frame anew, so consecutive frames of one scene differ by a few percent in brightness, and white balance drifts with them. Left alone, that shows up as flicker in the ghosts and a slight blur in the median. After warping, a gain per channel is estimated over the pixels both the frame and the reference cover, and applied before the frame enters the stack. Per channel rather than one luminance gain, because white-balance drift is exactly a different gain per channel. A gain, not an offset, because a camera's exposure change is multiplicative. A gain, not a full histogram match, because a ratio of channel means over a subsample of the overlap is a few operations per pixel, is clamped to a sane range, and holds up when a moving object covers part of it.

## Why the memory budget decides the working size

A fifty-frame burst at twelve megapixels is 2.4 GB of RGBA, more than a phone tab may hold, and a tab that runs out of memory is killed without a message. So the working size is not a fixed choice but the output of a budget: the frame count, the first frame's dimensions and the device's byte budget give the largest size at which the pipeline's peak fits, capped by the chosen output size and never upscaled. The peak is whichever is larger: aligning, when every aligned frame so far (three bytes per pixel each, plus five for the reference copy and the band in flight) sits beside the align workers, each holding its photo decoded at full size and a few working-size buffers; or rendering (37 bytes per pixel, once the frames and the workers are gone). The full-size decodes do not shrink with the working size, so they are paid first, and a device that cannot pay for them runs fewer align workers rather than a smaller picture.

The budget itself depends on the device. Chromium reports its memory, rounded and capped, and the pipeline takes a quarter of it, never less than the 256 MiB the app shipped with and never more than 2 GiB. Firefox and Safari report nothing, so the guess goes by input: 768 MiB on a touch device, an iPhone above all, and 1.5 GiB on a desktop. These numbers are a starting point, not a measurement; they are meant to be replaced by what real phones hold. A tab that runs out anyway is killed without a message on most phones; where the engine throws instead, the failure says the device ran out of memory and suggests a smaller size or fewer photos. The picker shows the size a burst will come out at from the same plan, before Combine is pressed, so the choice is made knowingly. A bigger burst comes out smaller, never crashes. The floor on the working long edge is where the result would stop being worth looking at; with at most a hundred photos the floor always fits the default budget, so the floor is used rather than a refusal. The budget is pure arithmetic in one function, tested as arithmetic, and the rest of the pipeline takes its answer as a size.

### Why a burst that does not fit is stacked in strips, not shrunk

The frames are the bulk of the peak, and nothing but the rows being stacked has to be in memory at once: the median of a pixel needs every frame's value at that pixel, not every frame's whole image. So when the frames do not fit whole, the rows are split into strips and each strip is stacked on its own. The alignment does not need doing again, only the decode and the warp: the homography, the exposure gain and the row runs of every frame are kept from the first pass, and the first strip's rows too, so the crop and the gain come out exactly as in one pass. The price is time, one more decode of every photo per strip, which is why the plan takes the fewest strips that fit, at most eight, and only shrinks the picture once eight do not fit either. A strip is a whole number of bands so it frees whole buffers, and the picker says in how many passes a burst will run before Combine is pressed. The same room is what makes the Original size possible at all; it stops at 4096 × 4096 pixels, the largest canvas Safari draws.

### Why frames are RGB bands with row runs, and the blur works in place

Every byte per pixel of a frame is paid fifty times over in a fifty-photo burst, so the frame format is where memory is won. The alpha channel of a decoded photo is always 255, so frames are stored as RGB. A coverage mask spends a byte per pixel on a set that is always one run per row (the warp maps the source rectangle to a convex region), so coverage is two numbers per row instead; the crop every frame covers follows from those runs alone, and only the crop is stacked. The frames are cut into bands of 64 rows, each its own buffer, so stacking can free a band as soon as its rows are folded in: the stack's own buffers grow into the room the frames leave, and the peak is the frames or the stack, never both. The composite blurs one colour channel at a time and does the vertical pass in place, keeping only the rows that will leave the window later, so rendering holds two single-channel float layers instead of six three-channel ones. None of this changes a single output value: the kernels are held to digests recorded before the change, so the memory saving is not a quality trade.

## Why a worker pool aligns and one worker stacks

Aligning is per frame and embarrassingly parallel: decode, detect, match, fit, warp, none of which needs another frame. A pool of `hardwareConcurrency − 1` workers, capped at four, uses the phone's cores without starving the UI thread that draws the progress. Stacking is the opposite: the median at a pixel needs that pixel from every frame, so the aligned frames must live in one place. A single stack worker keeps them, computes the three stack buffers once, and answers every slider change from those.

Between the two, buffers **move**, they are not copied: every worker message lists its transferables, so an aligned frame goes from its align worker to the stack worker without passing through the main thread's memory, and the main thread only ever forwards handles. The one exception is the reference frame, which the stack worker needs as the first entry and every align worker needs as features; it is decoded once, its features computed once, and both are sent out. Decoding happens inside the align workers too, so the main thread never touches pixels; `createImageBitmap` and `OffscreenCanvas` exist in workers for exactly this.

Both roles ship as **one worker script**. Turbopack starts every worker from the same bootstrap file and tells them apart only by a `#params=` URL fragment naming the chunks to load, and WebKit did not keep that distinction: in the browser suite the worker started for stacking ran the align code and rejected the first `add-reference`, while Chromium and Firefox ran both roles as written. A role that lives in a URL fragment is one a browser is allowed to lose, so there is nothing left to lose: `workers/exposure.worker.ts` serves both request families, `vision/pipeline/exposureService.ts` routes each request by type to the align handlers or the stack session, and a worker's role is only which requests the coordinator sends it. The cost is a stack session in every align worker, which holds nothing until an `add-reference` arrives, and the align code in the stack worker, chunks the browser has already fetched for the pool.

## Why the output is cropped to full coverage

Every warped frame covers the reference's rectangle only partly: the camera drifted, so a strip along one or two edges of each frame came from outside the source image. A pixel covered by fewer frames has a noisier median and a mean with a visible seam where the frame count changes. Rather than showing a border of degraded pixels, the stack finds the largest rectangle every aligned frame covers and crops to it. The cost is a few percent of the frame, which is what a hand-held burst costs anyway. A per-pixel coverage count would make the border usable at lower quality; nobody has asked for the border.

## Why export is a JPEG through a canvas and Web Share

The result lives as RGBA in the stack worker. Exporting draws it at working resolution onto a canvas and asks the browser for a JPEG: no encoder in the bundle, the browser's own hardware-backed one, and a format every phone gallery and chat accepts without conversion. On a phone the natural destination is the share sheet, so when `navigator.canShare({ files })` says the browser can share files, the JPEG goes to `navigator.share`; otherwise, and when sharing fails or is dismissed, it goes to a download link and the notice says so. PNG would be lossless and three times the size for a photograph; WebP would be smaller but still not universal in the places a long exposure gets sent to.

Saving goes through the browser's save dialog (`showSaveFilePicker`) where it exists, because a dialog can be cancelled and a cancel must not report "Saved as…"; the download link is the fallback, and it cannot tell a cancel from a save. On a touch screen the result image compares by press and hold (after 150 ms, so a scroll never flashes the photo) and only the slider thumb takes the finger, so scrolling from a track scrolls the page and dragging a thumb never does; the compare button stays for keyboard and mouse.

## Why Firefox and WebKit run in CI only

The pipeline stands on browser APIs whose behaviour differs by engine: `createImageBitmap` in a worker, `OffscreenCanvas`, file inputs, and the way each engine reports a worker error. A suite that runs on Chromium alone would not have caught, say, WebKit's orientation handling on a decoded bitmap, so the e2e projects cover Chromium (desktop and Pixel 7), Firefox and WebKit (iPhone 14), and iPhones are where most bursts are shot. Locally, though, Playwright's Firefox and WebKit builds come from a download host that some networks block, and a contributor without them should still be able to run the suite. So a local run may be limited to the Chromium projects, the developer guide says how to add the other two, and CI installs all four engines and is the run that counts. The post-deploy smoke test uses Chromium alone, because the deployed origin is the thing under test there, not the engine.

## Why the service worker fetches the shell network-first

GitHub Pages sends no cache headers the app controls, so the worker makes the content-hashed `_next/static/**` files cache-first: they change name when they change. The HTML, the manifest and the logo are fetched network-first and fall back to the cache only when the network fails. A shell served from cache after a deploy would name chunks the server no longer has, and with a static host there is nobody to redirect the request; network-first costs one round trip per navigation, which is what having no worker costs, and keeps the app opening offline from the cached copy.

One cache per build: the registration URL carries the build id, so each deploy installs a worker with its own cache and deletes the previous builds' caches, and only those. The prefix filter matters because every project page of an account shares one `github.io` origin, and with it Cache Storage.

## Why the bundle is precached at install from a build-time manifest

A worker that only caches what a controlled page asks for keeps a promise the README does not make: the first visit registers the worker after the page has loaded, so nothing is cached until the second visit, and the worker chunks are fetched only when a burst is combined, so combining offline works only for a visitor who combined online first. Precaching at install closes both gaps after one visit. The worker cannot find the bundle on its own, though: Turbopack hashes every chunk name, and the worker chunks are referenced from code, not from the HTML, so nothing but a manifest knows them. `scripts/precache-manifest.mjs` writes `out/precache.json` after `next build` (every file under `_next/static/**`, source maps excluded, sorted so a build is reproducible), and the install handler fetches it, with the build id as a cache buster, and adds the shell and every entry to that build's cache. The cost is about 1 MB on the first visit, downloaded once in the background; the hashed names make every later visit free. A missing manifest (`next dev` serves none) is a warning, not a broken app: the runtime strategies still fill the cache on demand.

A chunk served from the cache is handed out as a fresh `Response` copy rather than the stored object. Turbopack's worker chunk reads its bootstrap config from `location.hash` (`#params=...`), and a browser sets a worker's location from the response's URL, which for a stored response is the cache key with the fragment gone; a copy has no URL of its own, so the browser attaches the request's, fragment included. Without the copy, any combine served from the cache (the second one online, every one offline) failed with "Missing worker bootstrap config".

## Why the base path follows the Pages settings

A project site lives at `https://<owner>.github.io/ExposureBuddy/`, so every asset URL and the service-worker scope carry `/ExposureBuddy` and `next build` has to bake it in. Hard-coding the path would break the first fork under another name and any custom domain. Instead the deploy reads the site URL from the Pages settings (`actions/configure-pages`) and passes it to the build as `PAGES_BASE_URL`; its path becomes `basePath`, empty on a custom domain. A local build without the variable assumes `/ExposureBuddy`, and the e2e suite and Lighthouse serve the export under that path, because an export served at `/` 404s on nearly everything and the base path is the deployment fault the suite exists to catch.

## Why the CSP is a meta tag

GitHub Pages sets no response headers on the app's behalf, so the Content Security Policy is a `<meta http-equiv>` tag in the document head. A meta CSP cannot carry `frame-ancestors`, so a small inline script breaks the page out of a foreign frame instead (which deters casual framing only: a sandboxed frame that forbids top navigation defeats it, and a static host has no header to close that gap); `script-src` and `style-src` need `'unsafe-inline'`, since there is no server to mint a nonce and React writes style attributes; everything else is `'self'`, with `blob:` admitted for images because the picked photos' thumbnails are object URLs. A meta CSP governs the document only: dedicated workers take the policy delivered with their own script, which on a static host is none. The ZAP baseline ignores the header-only rules a static host can never satisfy, each with its reason written down, and fails on the one content rule (error text in shipped HTML) an export can get wrong.

## Why the app is bilingual with English as the default

The app is for people who shoot bursts, in Germany and elsewhere, so both German and English ship in one bundle: two dictionaries, a parity test that fails on a key missing from either, and one toggle that shows the other language's code. English is the default when the browser speaks neither, because it is the language of the documentation, of the repository and of most of the web the app will be linked from. The choice is remembered per device and applied before first paint, so `<html lang>` and the screen agree from the first frame, which is also what a screen reader needs.

## Why help lives in the app, and opens with Ctrl+/

The header's **Help** opens a short dialog in the app's own language rather than linking here: the docs are English-only and partly written for developers, and leaving the app strands an installed PWA that is offline. The dialog says what the app does, how to shoot, what the sliders do and what the privacy claim means; the edge cases stay in the [user guide](../how-to/user-guide.md). The shortcut carries a modifier because a bare `?`, the web's usual help key, is a single-character shortcut, which WCAG 2.1.4 allows only when it can be turned off or remapped. Ctrl+/ types nothing, so it works from inside a field too, and Shift stays allowed because a German keyboard types `/` as Shift+7.

## Why the deploy waits for CI on `main`

`pages-deploy.yml` starts from `workflow_run` when CI succeeds on `main`, and deploys that commit, not whatever `main` holds by then. Only the tip deploys: CI runs finish out of order and can be re-run, and deploying every green commit would let an older one publish over a newer bundle. A superseded run queues in a group of its own, so it cannot displace the tip's queued deploy. `workflow_run` is safe here because it only acts on `push` and `workflow_dispatch` runs of this repository, which only a collaborator with write access can start: `branches: [main]` alone also matches a fork's pull request from a branch named `main`. The hourly schedule is a sweep for a green tip whose CI run was started with `GITHUB_TOKEN` (a dispatch from another workflow), which starts no `workflow_run` of its own.

## Why mutation testing is scoped to the pure modules

Line coverage answers "did this run", not "would a real bug here have been caught", and for a kernel that is the whole question: a warp with the wrong sign on one term, a median that returns the mean, a budget that forgets the stack buffers all execute every line and produce a plausible image. So every module under `vision/` and the orchestration under `exposure/` (the coordinator, the hook, the worker port and server) is on the list in `mutation-targets.mjs`, which `vitest.config.mts` also reads for its per-file 100% coverage floors, so the two cannot drift. Workers and canvases reach those modules through injected factories and pure handlers, which is what makes them mutable without a browser.

The rendering layer stays off the list. JSX and Tailwind class strings produce thousands of near-equivalent mutants, a multi-minute run and a score that means nothing; a component's behaviour is proven by its component test and its journey's e2e case. A scoped run finishes in minutes and produces a number worth acting on, which is why CI runs it on every PR rather than only on `main`. Incremental on PRs, full on `main`: Stryker's incremental mode cannot see a change in a module a target imports or in a dependency, so `main` reruns everything and seeds every PR's cache. There is no `Stryker disable` or `/* v8 ignore */` in `src/`; a survivor is a missing assertion or dead code to delete, and what genuinely remains stays visible in the report.

## Why the e2e fixtures are generated, never committed

The journey test needs a burst whose right answer is known: a background image, a walker, and every frame's transform and gain, so the spec can render the expected scene and compare. Real photos have no ground truth, and a directory of ONGs in git would be megabytes that change every time the scene changes. `npm run fixtures` writes the bursts from a seeded generator, byte-identical on every run, with a `meta.json` per burst; the directory is gitignored and CI regenerates it before every build the suite follows. Changing the scene is a change to one script, reviewed as code. The same generator writes a tiny burst for the fast path, two unrelated scenes for the error journey, and a file that is not an image.

## npm audit: what's overridden and what's accepted risk

`web/package.json`'s `overrides` pin transitive dependencies that `npm audit` flagged and that have a same-major patched version:

- `qs` → `6.16.0`, via `@lhci/cli`'s `express`. CI-only.
- `tmp` → `0.2.7` and `uuid` → `^14.0.2`, from `@lhci/cli`. Both reached only by `lhci open`, which this project never runs; the calls each package makes stayed source-compatible.
- `eslint` → `$eslint` (the direct ESLint 10) under `eslint-plugin-import`, `eslint-plugin-react`, `eslint-plugin-react-hooks` and `eslint-plugin-jsx-a11y`, whose installed releases declare peer ranges that stop at ESLint 9 and which `eslint-config-next` pulls in. Without the override, every `npm ci` prints `ERESOLVE overriding peer dependency`. The accepted risk: a rule that silently stops reporting under ESLint 10 would look like a clean lint run. Revisit when a plugin widens its `eslint` peer range, and drop that entry.

Accepted risk: `extract-zip`, unresolved upstream, four levels under `@lhci/cli` (`@lhci/cli` → `lighthouse` → `puppeteer-core` → `extract-zip`). Only the Chrome-download path calls it, and `scripts/lighthouse.mjs` points Lighthouse at Playwright's existing Chromium, so that path never executes. It is CI-only tooling in `devDependencies` that `next build` never loads, so it cannot reach the bundle. Revisit if `@lhci/cli` moves past that chain.

Everything `next build` loads (`tailwindcss`, `@tailwindcss/postcss`, `typescript`) is in `dependencies`, and `setup-web` installs with `--ignore-scripts`, so a package that only reaches the CI runner stays a smaller risk than one that reaches every visitor's browser.

**Do not run `npm audit fix` here**, not even without `--force`: it reshuffles unrelated transitive versions. A from-scratch `rm -rf node_modules package-lock.json && npm install` re-resolves the whole tree against current advisories and can produce a worse baseline than the committed lockfile. Add a targeted `overrides` entry and run `npm install`.
